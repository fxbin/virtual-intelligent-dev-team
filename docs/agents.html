Agent catalog · v6.0.19

八个专家，一个责任中心。

系统不会让所有角色同时发言。每个任务只选择一个 Lead，协作角色必须有明确输入、输出、证据和退出条件。

路由原则八个角色Stage Councils路由示例
Routing principles

角色数量不代表系统能力，责任清晰才代表。

路由以任务的主要风险和最终产物选择 Lead，再以边界缺口决定是否需要协作。

One lead

唯一 Lead

负责目标、范围、WorkOrder 和最终交付决定。不会用“集体共识”掩盖无人负责。

Bounded support

按缺口协作

协作者只处理清楚的子范围；交接对象、证据和回收点必须可见。

Escalate by risk

风险驱动升级

只有跨领域、生产风险、重复失败或显式多 Agent 请求才增加治理重量。

Specialist roster

八个角色，各自拥有明确的“该做”与“不该做”。

下面是公开摘要；运行时真源仍以 references/agent-catalog.md 为准。

AGENT / 01

Java Virtuoso

负责 Java 21、Spring Boot、JVM 性能、并发策略与遗留 API 迁移。

  • 适合：Java / Spring 实现与性能
  • 不适合：纯 UI、商业战略、Git-only
  • 证据：JVM 版本、启动参数、回归或基准
javaspringjvm
AGENT / 02

Sentinel Architect (NB)

负责高风险变更、研究优先交付、分阶段迁移与回滚治理。

  • 适合：生产关键重构、敏感迁移
  • 不适合：低风险的一步修复
  • 证据：风险矩阵、检查点、回滚触发条件
high-riskmigrationgovernance
AGENT / 03

Technical Trinity

负责通用后端、系统设计、可靠性、DevSecOps-aware 实现与技术落地。

  • 适合：API、服务、Python / Go / Node / Rust
  • 不适合：定价、融资、纯视觉重设计
  • 证据：语言门禁、接口契约、回归结果
backendsystem-designreliability
AGENT / 04

Code Audit Council

负责代码审查、安全评估、可维护性分析与按严重度排序的修复建议。

  • 适合：review、audit、vulnerability
  • 不适合：无代码上下文的泛策略
  • 证据：受影响范围、严重度依据、修复路径
reviewsecurityquality
AGENT / 05

Git Workflow Guardian

负责分支策略、staged Git workflow、提交推送、PR、rebase 与 worktree 安全。

  • 适合：commit、push、PR、release hygiene
  • 不适合：纯代码实现或商业讨论
  • 证据：分支状态、ahead-behind、CI 与 PR
gitreleaseworktree
AGENT / 06

World-Class Product Architect

负责产品定义、用户流、验收、Beta、UI/UX、前端方向、设计系统与可访问性。

  • 适合：PRD、原型、React、dashboard
  • 不适合：纯后端基础设施
  • 证据：用户流、验收标准、影响范围与 a11y
productui-uxbeta
AGENT / 07

Data Pipeline Guardian

负责 ETL/ELT、流处理、数据质量、schema 演进、血缘和数据可观测性。

  • 适合：Kafka、Spark、Airflow、dbt、CDC
  • 不适合：无管道影响的一次性 SQL
  • 证据：拓扑、质量规则、schema 与失败策略
datapipelineschema
AGENT / 08

API Contract Sentinel

负责 OpenAPI / AsyncAPI、契约优先、版本治理、安全、幂等和 breaking change。

  • 适合：REST、GraphQL、gRPC、contract lock
  • 不适合：无 API 影响的纯 UI
  • 证据：规范、客户端影响、迁移与威胁模型
apicontractcompatibility
Stage councils

专家团是阶段 overlay，不是新的顶层团队。

两个 Council 都由 World-Class Product Architect 负责，只在阶段内展开 specialists；任务 Lead 和总体责任链不会被替换。
